# Codex subagents, teams, swarms, and workflows

Snapshot: 2026-07-12 20:28:55 CEST

Repository: `openai/codex` fork at commit `9e552e9d15ba52bed7077d5357f3e18e330f8f38` (2026-07-11)

Scope: the implementation in this checkout, plus the tool surface exposed in the session that produced this report.

## Executive summary

Codex currently has three related but distinct multi-agent mechanisms:

1. **Stable multi-agent v1**: enabled by default under the `multi_agent` feature. It exposes `spawn_agent`, `send_input`, `wait_agent`, `resume_agent`, and `close_agent`, normally under the `multi_agent_v1` namespace. Agents are addressed primarily by thread UUID.
2. **Multi-agent v2**: under development and disabled by default under `multi_agent_v2`. It uses canonical task paths such as `/root/research_api`, mailbox-style messages, and the tools `spawn_agent`, `send_message`, `followup_task`, `wait_agent`, `interrupt_agent`, and `list_agents`. The default namespace is `collaboration`.
3. **CSV agent jobs / fan-out**: under development and disabled by default under `enable_fanout`. It maps CSV rows to short-lived worker subagents, collects structured results, and exports a result CSV. This is the closest current implementation to a formal “swarm” primitive.

The exact product terms **“swarm”** and **“team”** are not first-class runtime entities in this code. The implementation speaks in terms of threads, subagents, agent control, agent paths, collaboration tools, roles, and agent jobs. A “team” is effectively one root thread plus its spawned thread tree sharing one `AgentControl` and `session_id`. A “workflow” is mostly model-orchestrated; there is no general declarative DAG/workflow engine for dependencies, retries, barriers, or handoffs.

Subagents are **not separate Codex OS processes**. Each is a `CodexThread`/`Session` in the same Codex process, with its own submission loop, turn tasks, context/history, event stream, status, and persisted rollout. The session loop and turns are Tokio tasks. Tool calls made by an agent may spawn child OS processes, but the agent itself has no dedicated PID.

All agents in a tree normally share:

- the same Codex process and `ThreadManager`;
- one tree-scoped `AgentControl` and `session_id`;
- the same container, working directory, and filesystem;
- the same base tool capabilities, subject to model, feature, role, and config-layer differences.

They do **not** have isolated worktrees by default. Concurrent edits are immediately visible to peers, so write ownership must be coordinated explicitly.

The session used to create this report exposes the **v2-style** surface (`/root` task paths and the `collaboration` namespace), even though the repository’s product default is still stable v1.

### Defaults and limits

Stable v1 effective defaults:

- up to 6 open subagent threads (`DEFAULT_AGENT_MAX_THREADS = Some(6)`);
- maximum spawn depth 1 (`DEFAULT_AGENT_MAX_DEPTH = 1`), yielding a root-with-workers topology unless configured otherwise;
- completed agents remain open and count against the limit until closed;
- `wait_agent` defaults to 30 seconds and clamps waits to 10 seconds through 1 hour.

V2 defaults:

- 4 concurrent threads per session **including the root**, so at most 3 subagent turns run concurrently by default;
- 30-second default wait, configurable from 0 through 1 hour, with a default minimum of 10 seconds;
- no v1-style spawn-depth enforcement; task paths may form deeper trees;
- completed, errored, or interrupted idle subagent sessions may be unloaded by an LRU residency policy and reloaded from persisted history when contacted;
- `agents.max_threads` is rejected when v2 is enabled; use `features.multi_agent_v2.max_concurrent_threads_per_session` instead;
- `agents.max_depth` exists but v2 spawn deliberately ignores it;
- by default, v2 agent tools are direct model tools and are excluded from the nested code-mode executor surface (`non_code_mode_only = true`);
- spawn metadata controls (`agent_type`, model, effort, service tier) are hidden by default (`hide_spawn_agent_metadata = true`).

V2 separates two related limits:

- **execution concurrency**: active subagent turns, with the root excluded from the limiter after its slot has already been accounted for;
- **residency**: how many v2 subagent sessions remain loaded in memory. Idle terminal sessions can be evicted and later rehydrated.

This means v2 can create more subagents over the lifetime of a session than can be simultaneously active or resident.

## What a subagent is internally

The object graph is approximately:

```text
ThreadManager
└── ThreadManagerState
    ├── threads: HashMap<ThreadId, Arc<CodexThread>>
    └── root CodexThread
        └── SessionServices
            └── AgentControl  (shared by the complete root tree)
                ├── AgentRegistry
                ├── AgentExecutionLimiter
                ├── V2Residency
                └── RolloutBudget

CodexThread
└── Codex
    ├── submission channel
    ├── event channel
    ├── AgentStatus watch channel
    ├── Session
    └── Tokio session-loop task
        └── Tokio task per active turn
```

Relevant implementation:

- `codex-rs/core/src/thread_manager.rs`: owns the in-memory `HashMap<ThreadId, Arc<CodexThread>>` and creates/resumes/forks threads.
- `codex-rs/core/src/codex_thread.rs`: defines the bidirectional thread conduit.
- `codex-rs/core/src/session/mod.rs`: spawns the per-session Tokio submission loop.
- `codex-rs/core/src/tasks/mod.rs`: spawns each turn as a Tokio task with a cancellation token.
- `codex-rs/core/src/agent/control.rs`: tree-scoped control plane shared by root and descendants.
- `codex-rs/core/src/agent/registry.rs`: in-memory agent metadata, paths, nicknames, and v1 open-thread accounting.
- `codex-rs/core/src/agent/control/execution.rs`: v2 active-turn concurrency.
- `codex-rs/core/src/agent/control/residency.rs`: v2 LRU load/unload behavior.

### Thread identity and persistence

Each subagent has:

- a `ThreadId` (UUID identity);
- a `SessionSource::SubAgent` classification;
- for ordinary spawned agents, a parent thread ID and depth;
- in v2, a canonical `AgentPath` such as `/root/indexer/parser`;
- an optional nickname and role;
- its own transcript/rollout and app-server event stream;
- a status derived from emitted lifecycle events.

Spawn edges are persisted in SQLite in `thread_spawn_edges`, with `open` or `closed` status. This lets the app-server list direct children or all descendants and lets v1 resume an open descendant tree. Ephemeral threads do not persist graph edges.

Agent statuses are:

- `pending_init`
- `running`
- `interrupted`
- `completed(message | null)`
- `errored(message)`
- `shutdown`
- `not_found`

`interrupted` is intentionally non-final: the thread remains reusable.

## Spawn and context inheritance

### Shared runtime configuration

A spawned child starts from the parent turn’s live effective config, not merely stale startup config. Codex copies or refreshes:

- base instructions;
- selected model/provider and reasoning settings;
- developer instructions;
- service tier;
- approval policy and approval reviewer;
- permission profile/sandbox;
- current working directory;
- selected environments and, where compatible, the parent execution-policy manager.

A role-specific config layer may then be applied. Runtime-owned approval, permission, sandbox, and cwd values are applied again after role selection so the child remains aligned with the live parent turn.

### V1 context modes

V1 `spawn_agent` starts with only its explicit initial prompt by default. `fork_context = true` forks the full parent thread history. Full-history forks inherit the parent role/model/reasoning and reject explicit overrides for those fields.

### V2 context modes

V2 `spawn_agent` accepts `fork_turns`:

- `none`: no surrounding parent history;
- `all`: full filtered history, and the default when omitted;
- a positive integer string such as `3`: only the last N turn boundaries.

Forked history is deliberately filtered. It keeps system/developer/user messages, final assistant answers, session metadata, compaction markers, and selected context state as appropriate. It drops reasoning, tool calls and outputs, inter-agent mail, and other transient execution items. This reduces chain-of-thought and tool-state leakage while providing useful task context.

Full-history v2 forks also require inherited role/model/reasoning; shorter or context-free forks may apply permitted overrides.

## Agent roles: capabilities, not team membership

Built-in roles are currently:

- `default`: ordinary agent;
- `explorer`: tuned for focused codebase questions and parallel exploration;
- `worker`: tuned for execution/implementation with explicit file ownership.

Users can declare roles below `[agents.<role>]` with:

- a human-facing `description`;
- an optional `config_file` containing a role-specific config layer and developer instructions;
- optional `nickname_candidates`.

Roles can alter model/config/instructions and tool availability through normal config layering. They do not create a scheduler, permission hierarchy, or a team object. The root is “coordinator” only by prompt and convention, not because workers are a weaker runtime class.

Example:

```toml
[agents]
max_threads = 6
max_depth = 2
interrupt_message = true

[agents.researcher]
description = "Research-focused role"
config_file = "./agents/researcher.toml"
nickname_candidates = ["Herodotus", "Ibn Battuta"]
```

The role file can contain ordinary Codex configuration plus `developer_instructions`. Relative paths are resolved relative to the declaring config file.

## How agents communicate

There are two data planes in addition to the shared filesystem.

### Stable v1: submitted user input and completion injection

V1 communication uses thread UUIDs:

- `send_input(target, message/items, interrupt)` submits ordinary input to a child thread;
- `interrupt = false` queues/starts the new input normally;
- `interrupt = true` first interrupts the current child turn, then submits the replacement input;
- `wait_agent(targets, timeout_ms)` subscribes to status watch channels and returns when at least one target becomes final;
- when a spawned child finishes, a watcher injects a bounded synthetic notification into the direct parent’s context; completed status includes the final assistant message.

This is less structured than v2 mail. It does not carry canonical sender/recipient task paths through a mailbox envelope.

### V2: `InterAgentCommunication` mailbox

V2 communication uses a structured record:

```text
InterAgentCommunication
├── id
├── author: AgentPath
├── recipient: AgentPath
├── other_recipients: Vec<AgentPath>
├── content or encrypted_content
├── metadata passthrough
└── trigger_turn: bool
```

Current collaboration tools send to one recipient; the protocol has `other_recipients`, but the exposed tools do not currently provide broadcast/multicast arguments.

The exposed operations are:

| Tool | Delivery semantics |
|---|---|
| `spawn_agent` | Creates a child path and sends a `NEW_TASK`-style initial communication that triggers the first turn. |
| `send_message` | Queue-only mail. It is delivered promptly to an active agent at safe sampling/message boundaries, or remains queued for a later turn. It does not independently wake an idle agent. |
| `followup_task` | Trigger-turn mail. It wakes an idle non-root target, or reaches a running target at safe message boundaries/after pending tool work. |
| child final answer | Sent automatically to the direct parent as a queue-only `FINAL_ANSWER` envelope. |
| `wait_agent` | Waits for mailbox activity, user steering, or timeout; it intentionally returns only a summary, not message content. The content becomes model input. |

Encrypted tool arguments are rendered to the receiving model with envelopes resembling:

```text
Message Type: NEW_TASK | MESSAGE | FINAL_ANSWER
Task name: /root/...
Sender: /root/...
Payload:
...
```

Messages are queued in each session’s `InputQueue`. While an agent is sampling, mailbox activity can cause a follow-up inference after safe boundaries. Once visible final-answer text establishes an answer boundary, new mail is deferred to the next turn rather than mutating the already-finished answer.

### Address resolution in v2

- `/root` is the canonical root.
- Spawning `task_name = "parser"` from `/root/indexer` creates `/root/indexer/parser`.
- A relative target is resolved below the sender’s current path.
- An absolute `/root/...` target can address another branch.
- Task names allow lowercase ASCII letters, digits, and underscores.
- `root`, `.`, `..`, slash-containing names, and duplicate live paths are rejected.
- `send_message` may target root; `followup_task` may not target root.
- An agent cannot interrupt itself, and root is not a valid `interrupt_agent` target.

### Shared filesystem as an implicit communication channel

All agents see edits immediately. This is useful for parallel implementation but is not transactional messaging:

- there is no automatic file locking;
- there is no per-agent Git worktree;
- there is no automatic merge of independent patches;
- one agent can observe partially completed changes from another;
- overlapping writers can race or overwrite each other.

The practical coordination rule is to assign disjoint file/module ownership and have the root review/integrate the combined state.

## Supported topologies

### 1. Coordinator with workers (star)

```text
/root
├── worker_a
├── worker_b
└── reviewer
```

This is the ordinary and safest pattern. It is also the effective default in v1 because default `max_depth = 1` prevents workers from spawning grandchildren.

### 2. Fan-out / fan-in

```text
              ┌── explorer_api ──┐
/root ────────├── explorer_ui  ──┼── root integrates
              └── test_runner  ──┘
```

The root spawns independent siblings, keeps doing non-overlapping work, then waits for completion/mailbox updates and integrates results. There is no atomic barrier primitive; v1 waits on explicit targets, while v2 waits for any mailbox activity and uses `list_agents` to refresh status.

### 3. Hierarchical tree

```text
/root
├── backend
│   ├── api
│   └── storage
└── frontend
    ├── view
    └── tests
```

V1 supports this only when `agents.max_depth` is increased. V2 task paths naturally represent it and do not enforce the v1 depth limit. Every descendant shares the same root-scoped `AgentControl`, concurrency limit, rollout budget, filesystem, and session ID.

### 4. Peer-to-peer messaging

V2 agents can communicate across branches using absolute canonical paths. V1 can submit to another known UUID. The runtime does not enforce a strict parent-only message topology, although final results are automatically routed only to the direct parent.

### 5. Pipeline / staged handoff

One agent can send a follow-up task to another after producing an artifact, for example researcher → implementer → reviewer. This is model-driven choreography, not a persisted workflow DAG. Codex does not natively encode prerequisites, exactly-once handoffs, compensation, or retry policies for general agent pipelines.

### 6. CSV map workers (“swarm-like” fan-out)

With `enable_fanout`, `spawn_agents_on_csv`:

- reads one local CSV;
- creates one persisted job item per row;
- expands `{column_name}` placeholders into an instruction template;
- spawns one short-lived `SubAgentSource::Other("agent_job:<id>")` worker per active row;
- defaults to 16 concurrent workers, hard-caps at 64, and further caps by the effective agent-thread limit;
- defaults each worker runtime to 30 minutes unless configured/requested otherwise;
- requires every worker to call `report_agent_job_result` exactly once;
- fails workers that finish without reporting;
- allows a worker report with `stop = true` to cancel the job and prevent additional pending rows from being spawned; already-running workers are allowed to finish or time out;
- shuts down each worker after finalization;
- stores job/item state in SQLite and exports a CSV snapshot;
- currently requires exactly one local environment and does not support remote environments;
- blocks the parent tool call until the complete job ends.

This is a specialized map operation, not a general swarm consensus or emergent coordination system. Workers do not negotiate with one another.

### Not currently first-class

- declarative teams with membership and team-level policy;
- dynamic leader election;
- shared blackboard/state object other than files, SQLite internals, and messages;
- voting, debate, consensus, or quorum primitives;
- a general DAG scheduler;
- multicast/broadcast collaboration tools;
- per-agent containers or worktrees;
- an agent PID that can be individually killed with an OS signal;
- a bulk `interrupt_all_agents` or `close_all_agents` collaboration tool.

## How to observe a particular subagent

### From the TUI

1. Use `/agent` (alias `/subagents`) to inspect or switch agent threads.
2. Use `Alt+Left` and `Alt+Right` to cycle through tracked threads in first-seen spawn order.
3. V1 history renders spawn, send, wait, resume, and close items with nicknames, roles, prompts, status, model, and reasoning effort where available.
4. V2 `/agent` status output shows running canonical task paths and a bounded preview of recent activity such as messages, reasoning summaries, commands, file changes, MCP calls, web searches, and nested agent actions.
5. Switching to a thread reconstructs its transcript from app-server events/history. Closed v1 threads remain inspectable in the picker.

Important v2 limitation: app-server `turn/start` and `turn/steer` reject direct input to a spawned v2 subagent. Viewing its transcript is supported, but steering should go through the root/peer collaboration mailbox. A direct `turn/interrupt` remains available for an active turn.

### From a model/agent in v1

- Keep the returned `agent_id` from `spawn_agent`.
- Call `wait_agent` with one or more explicit IDs.
- The result maps each target to its latest final status and includes a completed final message.
- Use `send_input` for additional work; `resume_agent` can rehydrate a closed persisted thread.

### From a model/agent in v2

- Keep the returned canonical task name, not just a nickname.
- Call `list_agents` to get live `agent_name`, `agent_status`, and `last_task_message`; optionally filter by a task-path prefix.
- Call `wait_agent` to sleep until any mailbox/final notification arrives, then let the next inference consume the message and/or call `list_agents` again.
- `list_agents` describes currently live/loaded agents. A terminal agent evicted by v2 residency may be absent even though its stored thread can later be reloaded when addressed.

Example v2 flow:

```text
spawn_agent(task_name="api", message="Trace the API flow", fork_turns="all")
list_agents(path_prefix="/root/api")
wait_agent(timeout_ms=30000)
list_agents(path_prefix="/root/api")
```

### From an app-server client

The app-server is the strongest programmatic observation surface:

- every spawned thread has its own `threadId` and `sessionId`;
- initialized connections are best-effort attached to newly created thread listeners;
- subscribe to `turn/started`, `item/started`, deltas, `item/completed`, `turn/completed`, and `thread/status/changed` for that thread;
- `thread/loaded/list` reports currently loaded in-memory thread IDs;
- `thread/read { threadId, includeTurns: true }` reads a specific stored transcript without resuming it;
- experimental `thread/turns/list` and `thread/items/list` provide paginated history;
- `thread/list { parentThreadId }` lists direct children;
- experimental `thread/list { ancestorThreadId }` lists all descendants from persisted spawn edges;
- returned thread metadata includes `parentThreadId`, `agentNickname`, and `agentRole`; v2 `subAgentActivity` items also include `agentThreadId` and canonical `agentPath`.

### Lifecycle hooks

User-configured hooks can observe ordinary spawned children:

- `SubagentStart` runs when a thread-spawn child begins;
- `SubagentStop` runs when such a child turn stops and includes agent ID/type plus transcript paths.

Internal/synthetic subagents such as review/compact jobs do not expose these user-configured subagent hooks.

### Tracing and raw persistence

Advanced operators can inspect:

- per-thread JSONL rollouts/transcripts;
- SQLite thread and `thread_spawn_edges` metadata;
- app-server event streams;
- `codex.multi_agent.spawn` counters tagged by role and version;
- the `codex_otel.agent_communication` tracing target for send/receive events.

Communication tracing can include message content (or encrypted content), so enabling that target has privacy and secret-handling implications.

## How to steer agents

### V1

Use `send_input`:

```text
send_input(target=<thread UUID>, message="Narrow the task to parser.rs", interrupt=false)
```

- `interrupt=false`: queue a follow-up normally;
- `interrupt=true`: cancel the current turn and immediately redirect the agent with the new input;
- structured input items can carry text, images, local images, skills, or mentions.

Use `resume_agent(id)` before sending more work if the agent was explicitly closed and is no longer loaded.

### V2

Use `send_message` for advisory context that should not start an idle turn:

```text
send_message(target="api", message="The schema changed; account for field X")
```

Use `followup_task` when the target should perform another turn:

```text
followup_task(target="/root/api", message="Now add the missing integration test")
```

If the target is running, both forms are delivered at safe message boundaries; `followup_task` also wakes an idle target. To replace current work quickly, first `interrupt_agent`, then send `followup_task`.

For human steering:

- steer the root’s active turn with app-server `turn/steer` or the normal UI input path;
- ask the root to contact the named child;
- do not use `turn/start`/`turn/steer` directly on v2 spawned subagents, because the app-server rejects it.

## How to interrupt or kill agents

“Interrupt,” “close,” “unload,” “delete,” and “kill the process” are different operations.

| Operation | Scope | Effect | Reusable? |
|---|---|---|---|
| V2 `interrupt_agent(target)` | One child turn | Sends `Op::Interrupt`; returns previous status; thread stays known | Yes |
| App-server `turn/interrupt` | One active turn | Cancels the specified thread/turn | Yes |
| V1 `send_input(..., interrupt=true)` | One child turn plus replacement input | Interrupts and redirects | Yes |
| V1 `close_agent(target)` | Target and live descendants | Flushes rollout, sends shutdown, removes threads, marks target spawn edge closed | Yes, via `resume_agent` if persisted |
| V2 residency unload | One idle terminal child | Flushes/shuts down/removes in-memory thread to free a slot | Yes, automatic reload on contact |
| App-server `thread/delete` | Thread and persisted descendants | Destructive deletion of active/archive state and descendant rollouts | No |
| Kill Codex OS process | Every thread in that process | Abruptly terminates all agents and root | Only by restarting/resuming persisted threads |

### Particular v2 agent

Soft stop:

```text
interrupt_agent(target="/root/api")
```

Redirect immediately:

```text
interrupt_agent(target="/root/api")
followup_task(target="/root/api", message="Stop API work; investigate the failing migration")
```

There is no v2 collaboration `close_agent`. Interruption is the intended model-facing operation; terminal agents are managed by residency.

### Particular v1 agent

Use `close_agent(target=<UUID>)`. It cascades to live descendants. If you need the context later, use `resume_agent(id=<UUID>)` and then `send_input`.

### All agents

There is no atomic bulk collaboration command.

- **V2**: call `list_agents`, exclude `/root`, and issue `interrupt_agent` for each running target. Multiple independent tool calls may be issued in one model step where the client/runtime permits parallel tool calls. This is a best-effort snapshot, so newly spawned agents can race with the sweep.
- **V1**: close each root child; each close cascades through that child’s descendants. Closing all direct children therefore closes the tree without targeting the root.
- **App-server**: enumerate descendants with `thread/list { ancestorThreadId }` and interrupt active turns individually. Use recursive `thread/delete` only when permanent deletion is actually intended.
- **Emergency process-wide stop**: terminating the Codex process stops everything because subagents are in-process. It is not a selective subagent kill and may interrupt persistence/tool cleanup.

Because there is no per-agent OS process, `kill <pid>` cannot selectively terminate one agent. Kill a tool subprocess only when the problem is specifically that subprocess; doing so does not by itself update the owning agent’s lifecycle correctly.

## Configuration examples

### Stable v1

It is already enabled by default, but can be made explicit:

```toml
[features]
multi_agent = true

[agents]
max_threads = 6
max_depth = 2
interrupt_message = true
```

Setting `multi_agent = false` removes the collaboration tool surface for new turns, though clients may still inspect already-existing subagent threads.

### V2

```toml
[features.multi_agent_v2]
enabled = true
max_concurrent_threads_per_session = 4
min_wait_timeout_ms = 10000
default_wait_timeout_ms = 30000
max_wait_timeout_ms = 3600000
tool_namespace = "collaboration"
hide_spawn_agent_metadata = true
non_code_mode_only = true
```

Do not also set `agents.max_threads`; config validation rejects that combination.

The v2 multi-agent delegation policy is injected as developer context:

- ordinary effort: `ExplicitRequestOnly`, so user/AGENTS/skill authorization is required before spawning;
- Ultra reasoning effort: `Proactive`, which permits delegation when it materially helps;
- `multi_agent_mode_hint_text`: replaces those built-in policies with custom text, including an intentionally empty policy.

The old API/config `multiAgentMode` field is deprecated/ignored; the current effective mode is derived as above.

### CSV fan-out

```toml
[features]
multi_agent = true
enable_fanout = true

[agents]
max_threads = 32
job_max_runtime_seconds = 1800
```

`enable_fanout` normalizes the stable multi-agent dependency on, but remains under development.

## Practical operating guidance

1. Prefer a root coordinator with shallow, disjoint workers.
2. Spawn only concrete tasks that can proceed independently while the parent does useful work.
3. Give coding workers explicit file/module ownership.
4. Avoid overlapping writes because all agents share one filesystem.
5. Use roles for instruction/model/config specialization, not as a security boundary.
6. Keep canonical v2 paths or v1 thread IDs in your orchestration state; nicknames are presentation metadata.
7. In v2, use `send_message` for context and `followup_task` for work.
8. Treat `interrupt_agent` as cancellation, not deletion.
9. In v1, close completed agents to free open-thread capacity.
10. Observe through app-server per-thread events when building a UI or automation; polling only `list_agents` loses transcript detail and may miss unloaded terminal agents.
11. Use `thread/list` relationship filters to reconstruct persisted topology.
12. Enable communication-content tracing only with an explicit data-handling decision.

## Known rough edges and caveats

- V1 and v2 coexist in source but have incompatible tool semantics and identifiers.
- The stable app-server README’s `collabToolCall` examples are primarily v1-shaped; source types also include v2 `subAgentActivity` items.
- V2 is explicitly under development and configuration/schema may change.
- V2 `wait_agent` is an activity wait, not a target-specific join and not a result-returning future.
- V2 direct app-server input to children is intentionally forbidden.
- V2 has no exposed close/resume tools; persistence/residency performs rehydration internally.
- V2 explicitly truncates forwarded error details to fit a roughly 1,000-token completion envelope. Successful final messages are forwarded from the child as-is and rely on the ordinary model/output/context limits rather than that error-specific cap.
- Message delivery is coordinated around inference boundaries; it is not an immediate shared-memory callback into a model mid-token.
- The shared filesystem makes parallelism fast but non-isolated.
- The registry/control plane is scoped to a live root tree, not globally across all Codex threads.
- A stored thread resumed as a new root can establish a new live session tree/session ID relationship.
- Review, compact, memory consolidation, and other internal subagent sources exist but are not ordinary user-spawned team members and may have different hooks/tool behavior.
